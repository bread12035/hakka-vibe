# 15: 彙總報告

**What to build:** 將 24 個 arm、72 次 run 的結果整理成一份可據以決策的報告：哪些 harness 手段真的省錢、省多少、實作成本如何，以及哪些結論不可外推。這份報告的結論將決定後續 agent layer 與 MemoryStore 的設計。

**Blocked by:** 06, 08, 09, 10, 11, 12, 13, 14

**Status:** in-progress

- [x] 24 個 arm 的成本對照，一律以美元表述，token 細項作為診斷資料附列
- [x] 兩個 harness 的百分比分開呈現，並說明 TTL 不同使其單價基準不同
- [x] 各 arm 的中位數與最大最小值並列，變異幅度本身視為結果
- [x] 明載限制：所有數字建立在合成 fixture 之上，arm 之間的相對差異可信，絕對值不可外推至真實專案
- [x] 明載生成 fixture 與解題模型同屬一個模型家族所構成的效度威脅
- [ ] 依成本節省與實作成本的比值排序，指出下一步最值得投入的方向

## Comments

**狀態為 in-progress：目前沒有任何真實 run 資料**——14 張前置票全部還在等憑證。這張票
交付的是**報告產生器本身**，不是報告的實際內容；產生器已對合成資料完整驗證，等你在地端
跑過真實 experiment，`uv run python -m hakka_vibe.measurement.report` 就能把 `results/` 底下累積的
紀錄轉成 `results/REPORT.md`。目前產出的版本只有一句「還沒有資料」加上固定的限制段落，
已隨此 commit 一併生成、進版控。

已驗證（合成資料）：

- 完整的 arm（三次 run）算出美元中位數，欄位格式跟 `ArmSummary` 一致。
- **不完整的 arm 不會讓報告器崩潰**，會標成 `incomplete (N/3 runs)`——這條刻意設計，
  因為真實情況是 arm 會一個一個陸續跑完，不會全部同時到齊。
- Claude Code 執行的 arm（`2d`／`2e`）在報告裡明確標註「與自建 harness 不可比」，
  理由是兩者的 cache TTL 基準不同（依 ADR-0002）。
- **依成本節省排序、指出下一步最值得投入的方向**——這條驗收條件沒有實作：沒有真實
  數字可排序，硬做一個空排序沒有意義。等第一批真實 arm 資料進來後，這是下一步要補的
  邏輯，不是遺漏。

報告器讀取 `results/<experiment>/<arm>/*.json` 時**重新解析原始 usage 算出 `ArmSummary`**，
不依賴任何預先算好的彙總欄位——這跟 ticket 01 的「原始 usage 不做預先彙總」是同一個決定
的延伸：cost model 以後若被修正，重跑報告器就會用新公式重新計價全部歷史紀錄，不需要
重新執行任何一次真實呼叫。
